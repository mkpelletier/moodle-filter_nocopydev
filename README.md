# Tripwire (filter_tripwire)

A Moodle filter plugin for academic integrity. It plants a hidden citation honeypot in quiz essays and Q&A forum questions, so answers generated by AI tools can be recognised when marking, and it blocks copy, paste, the context menu, and developer tools shortcuts. Designed as one layer in a multi-layered exam security strategy.

Formerly **No Copy / Dev Tools** (`filter_nocopydev`).

## Features

- Blocks copy, cut, and paste (keyboard shortcuts and browser events)
- Blocks right-click context menu
- Blocks developer tools shortcuts (F12, Ctrl+Shift+I/J/C)
- Blocks view source (Ctrl+U) and save page (Ctrl+S)
- Blocks text selection via CSS
- Works inside TinyMCE editors (hooks into TinyMCE's internal event system)
- Displays a full-page blocking overlay when JavaScript is disabled
- Per-context toggling: can be enabled/disabled at site, category, course, or activity level
- Each blocked action (copy, cut, paste, selection, context menu, dev tools) can be allowed separately per context
- Quiz-attempt layers by question type (citation honeypot on essays; forensic watermark on MCQ, true/false, matching, and short answer)
- Citation honeypot on Q&A forum questions (paste stays allowed on forum pages)
- Fictional title highlighted for markers wherever a student has written it
- Citation honeypot configurable per category, course, quiz, or forum

## Automated tests

PHPUnit tests live in `tests/`. GitHub Actions runs the standard [moodle-plugin-ci](https://github.com/moodlehq/moodle-plugin-ci) suite (phplint, phpcs, phpdoc, validate, savepoints, mustache, grunt, PHPUnit, Behat) against Moodle 5.1–5.3 on PHP 8.2/8.3 with PostgreSQL and MariaDB. See `.github/workflows/ci.yml`.

Locally, sync into a Moodle test site, then from that site’s root (after `php public/admin/tool/phpunit/cli/init.php` if the suite is missing):

```bash
php vendor/bin/phpunit --testsuite filter_tripwire_testsuite
```

## Requirements

- Moodle 5.1+ (PHP 8.2+)

## Installation

1. Copy this repository into `/path/to/moodle/filter/tripwire` (on Moodle 5.1+, `/path/to/moodle/public/filter/tripwire`)
2. Visit **Site administration > Notifications** to install the plugin
3. Enable the filter at **Site administration > Plugins > Filters > Manage filters**

During development, after copying new JavaScript or language strings (especially when `version.php` has not changed), purge caches or Moodle will keep the old files. Local shortcut: `scripts/sync-local.sh` (rsyncs into the local 5.3 tree and purges its caches).

## Configuration

The filter can be set to:

- **On** - Active everywhere on the site
- **Off, but available** - Can be selectively enabled per category, course, or activity

For exam security, a typical setup is to set it to "Off, but available" at the site level and enable it on specific quiz activities.

Copy, paste, and the context menu are blocked only for the roles chosen under **Site administration → Plugins → Filters → Tripwire** (Student by default). Teachers reviewing or reporting on attempts are not locked unless they also have a restricted role in that course. **Preview quiz** (an in-progress attempt page) still applies the lockdown so staff can test the filter. **Switch role to Student** also applies it.

### Choosing what to block

Six actions can be allowed or blocked separately: **copy**, **cut**, **paste**, **text selection** (including Ctrl/Cmd+A), the **right-click menu**, and **developer tools shortcuts** (F12, Ctrl/Cmd+Shift+I/J/C, view source, save page). All are blocked by default.

Site defaults are on the plugin settings page. To change them for one category, course, or activity, open **Filters → Tripwire → Settings** there. Each box starts at the inherited value; only boxes you change are saved, so a later change on the course still reaches activities that never chose. For example, untick **Block paste** on an essay quiz to let students paste a drafted answer while copy, cut, and dev tools stay blocked.

Paste is always allowed on forum pages, whatever is set (see Q&A forums below). If every action is allowed in a context, the lockdown script is not loaded there.

Print / “Save as PDF” from the print dialog is blanked with `@media print`. Safari **File → Export as PDF** does not use print CSS (it snapshots the screen). That path cannot be made blank without hiding the quiz from the student; a graphical Safari PDF will still show the questions and should carry the forensic watermark. Author colours in the stem (for example a red letter in a Hebrew gapfill) are left intact, and answer inputs nested in the stem stay typeable.

### Citation honeypot (per course)

On quiz attempt pages, **essay** questions receive a hidden scholarly instruction: a **real author** paired with a **fictional work**. It is white-on-white at the end of the stem (copy/select is blocked). Tools that scrape visible page text — including Brave Leo — often cite it. A marker who knows the field will spot the fake title immediately. Screen readers will speak it, so students who use one should be excused (see *Assessment arrangements* below). Short-answer items do not get the canary.

Set this on the **course**, not the site, so the author belongs on that reading list:

1. In the course, go to **More → Filters** (or **Course administration → Filters**)
2. Enable **Tripwire**
3. Click **Settings** next to it
4. Enter an author your markers will recognise and a title that author never published

Leave a field blank to inherit from the parent context (quiz ← course ← category ← site). A quiz can override the course, or disable the honeypot without clearing the parent.

Site administration defaults are only a fallback. Prefer leaving them empty so each course plants its own citation — a single site-wide title will leak across the student body in a week.

When marking, search scripts for the fictional **title**. Author-alone is too common in legitimate essays.

Selected-response items (multiple choice, true/false, matching) do not receive the citation. Their submission is a click, so the canary cannot come back. Those items get a bland forensic watermark instead.

### Q&A forums

Enable the filter on a **Q&A forum** and set a citation on the forum or its course, exactly as for a quiz. The question post of every discussion then carries the hidden citation for restricted roles (Student by default). Staff never receive it; use **Switch role to Student** to check.

Only the Q&A type is baited. A student there cannot read anyone else's answer before posting their own, so a fictional title in a first answer can only have come from the question. In any other forum type the first student to take the bait shows it to the whole class, and later citations prove nothing. After a student has answered they can read peers' posts, so treat a title that first appears in a later reply as weaker evidence.

On every forum page **paste is allowed** for students. Replies are often drafted elsewhere, and a pasted AI answer brings the citation back unedited. Copying out, selecting, and the context menu stay blocked. Forums get no watermark.

Not covered: forum notification emails, the Moodle mobile app, and RSS deliver the question as plain copyable text with no citation, because the honeypot is added in the browser. Do not force subscription on a baited forum.

A screen reader will speak the hidden citation on every visit, not during one sitting as in a quiz.

### Assessment arrangements

Screen readers and AI page readers see the same hidden text, so the honeypot cannot be hidden from one and not the other. Students who use assistive technology are excused instead: users with `filter/tripwire:skiphoneypot` receive no citation in quizzes or forums. Lockdown and the forensic watermark still apply.

No role has the capability by default. To set it up:

1. Create a role (for example *Assessment arrangement*) that can be assigned in the **System** context, with `filter/tripwire:skiphoneypot` allowed and nothing else.
2. Assign it under **Site administration → Users → Permissions → Assign system roles**, at the request of the student and your disability or accommodations office.

Assign it at system level only. Roles assigned in a course appear on its Participants page; system roles do not, so teachers never learn who is excused. The name records an arrangement, not a reason. The plugin stores nothing about these users and shows no difference to markers. Site administrators can still see who holds the role.

Site administrators are not excused automatically, so Preview quiz still shows them the citation.

### Highlight for markers

Users with `filter/tripwire:viewhoneypothits` (teachers and managers by default) see the fictional title highlighted wherever the filter is active and a student has written it: forum posts and quiz responses. Nothing is logged or stored; a student who edits the title out during the forum's editing window leaves no trace.

## Important Notes

This filter is a **deterrent, not absolute security**. A technically skilled user can bypass client-side JavaScript protections. It is intended to be used as one component in a layered security approach (e.g., alongside Safe Exam Browser, proctoring, etc.).
